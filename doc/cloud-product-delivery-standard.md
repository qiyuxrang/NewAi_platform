# 云端产品事业部交付标准

记录日期：2026-10-11。

用户明确的最终要求：可以部署到云服务器、稳定生成产品事业部三件套、界面采用 Workbuddy 风格。本文件定义验收目标与当前差距，不代表部署或生成验收已经完成。

## 范围与待确认项

- 用户已确认三件套：技术方案 DOCX、可行性研究报告 DOCX、汇报 PPTX。
- 用户已确认部署目标：Linux 云服务器 + Docker。
- Workbuddy 风格暂指网页工作台的布局、视觉与任务交互。报告及 PPT 保留现有正式文档规则和模板，除非用户进一步要求改变成果风格。
- 首期验收重点是产品事业部。保持人事、工程、总经理与管理后台的现有权限边界，迁移不得造成回归。

## 必须达到的交付结果

### 云端部署

- 能从源码及依赖清单在干净服务器构建，不依赖开发者桌面路径、复制的虚拟环境或既有 SQLite 业务快照。
- 提供镜像构建文件、生产 Compose、环境变量模板、迁移命令、初始化及部署说明。
- 前端使用生产构建；外部入口采用域名和 HTTPS，数据库及内部服务仅在受控网络访问。
- 网关数据库与业务数据库均使用 PostgreSQL；业务资料、成果和 Agent 数据持久化，升级或重建容器不能丢失。
- 模型网关、外部知识服务、中文字体、文档与图表渲染依赖可配置并有就绪检查。
- 服务自动重启；任务 Worker 有租约、恢复与重复领取保护。提供日志、健康检查、备份恢复和版本回滚说明，并实际演练。
- 多账号不能读取其他人的源文件、任务或成果；权限变化后及时拒绝访问，凭据不得出现在浏览器响应与日志中。

### 三件套生成

- 完整操作链：新建项目 → 上传资料 → 解析及授权检索 → 蓝图确认 → 分章节生成两份报告 → 内容核对 → 图表与文档渲染 → 基于报告制作 PPT → 审核、预览和下载。
- 用户可以从同一项目发起三件套，并查看每份成果的真实状态、版本、失败原因和下一步操作。
- 资料不足、蓝图矛盾或内容审核未通过时进入明确的待补充或待审核状态，用户通过正常页面补充后可继续；不能静默放宽质量检查。
- 报告与 PPT 使用同一输入和已确认蓝图；PPT 来源于当前报告，不额外编造参数、价格和结论。
- 三份文件真实存在、哈希匹配、可打开、可编辑、可下载；用户审批和文件生成状态分别展示。
- 保留既有技术方案与可研长度、图表和模板规则，除非用户明确调整。当前新建页面写有技术方案不少于 50,000 字/15 图、可研不少于 70,000 字/20 图，需与后端规则核对后统一。
- Word 目录、页码、中文字体、表格、图片和图表经过真实渲染验收；PPT 验证文本与图表可编辑、中文正常、无溢出、来源映射可核对。

### 稳定性验收

以下为建议的初始验收样本规模，正式执行前结合服务器规格、模型费用及用户资料确定。

| 场景 | 通过条件 |
| --- | --- |
| 完整资料样本 | 至少 3 个不同项目，每个完成 2 次独立生成，均得到可用三件套并通过内容与排版核对 |
| 缺项资料样本 | 明确提示缺项，补充后可续跑，保留有效内容和历史版本 |
| 模型超时、限流、格式错误 | 重试有界、错误可追踪、已完成章节保留；不可无限重试或伪报完成 |
| Worker 崩溃及服务重启 | 有效租约过期后正常恢复，不重复产生当前成果，不丢失已保存内容 |
| 渲染失败 | 可重新渲染，已完成正文和其它成果不受损 |
| 浏览器刷新与断开 | 后台继续执行，重新打开能恢复真实进度 |
| 两个账号同时生成 | 来源、进度、文件及权限隔离，资源和模型并发受到配置上限约束 |
| 取消 | 停止后续执行，取消后不发布迟到成果；页面保持真实状态 |
| 输入或蓝图变更 | 旧成果不误标为当前，新成果明确关联新版本 |
| 备份恢复 | 在独立环境恢复数据库、资料及成果并完成下载与权限验证 |

记录每个项目的输入版本、模型与调用量、耗时、重试次数、三份文件哈希、审核与渲染结果。单元测试与模拟生成不能替代目标云服务器上的真实端到端验收。

### Workbuddy 风格工作台

- 左侧：新建任务、项目/任务列表、资料入口，底部放账号与设置。
- 中间：项目任务对话、资料上传、阶段进度和待处理事项；蓝图与内容确认在当前任务上下文完成。
- 右侧：可收起的成果面板，展示技术方案、可研、PPT，支持预览、版本查看与下载。
- 将分散页面组织成围绕项目的工作流；用户能快速判断当前阶段、需要补充什么、已经得到什么。
- 具体配色、字体、间距及组件在视觉稿中确定；用户要求的是风格参考，保留本项目名称与品牌。
- 验证 1440×900 与 1280×720 桌面布局；窄屏折叠侧栏和成果面板。键盘操作、焦点、上传、长任务和失败状态均需可用。
- 预览或演示数据必须与真实任务状态区分；正式页面接现有授权 API，不能用静态成果代替实际交付。

## 实施顺序与完成证据

1. 明确三件套、目标云环境和成果模板；统一生成与部署配置基线。
2. 建立生产部署及文档渲染链路，在干净环境完成构建、迁移、就绪检查和样本渲染。
3. 完善三件套编排及恢复能力，完成一个真实项目从输入到三份可用文件的闭环。
4. 将该流程接入 Workbuddy 风格工作台，验证预览、补充、审核、续跑和下载。
5. 完成多样本、故障恢复、并发隔离及备份恢复验收，交付部署包、运维说明和验收证据。

三项硬条件（云端部署、稳定三件套、工作台风格）全部有实际证据后才能声明最终交付完成。

2026-10-11 已实施 Linux Docker 部署候选包、显式 LibreOffice 渲染后端、产品三件套默认入口，以及 Workbuddy 风格的任务/工作区/成果面板。原有 Windows Word 路径和业务审批继续保留。上表记录改造前的差距；镜像冷构建、实际 Linux 渲染与真实项目稳定生成仍须在目标服务器验收。本阶段按用户要求先交付部署包，详见 `deploy/cloud/README.md` 和 `doc/cloud-package-verification.md`。
