## 1. 审批摘要

## 4. 用户流程与界面

### 4.0 部门填报到总经理

1. 售前员工在“售前填报”保存自己的项目，工程员工在“工程填报”维护项目状态和进度，财务员工在“财务填报”维护应收、回款等记录。
2. 售前、工程沿用现有保存草稿、授权提交和发布流程；财务沿用本人精确记录发布。用户没有要求取消这些规则，因此本版默认已发布版本对总经理可见，未发布修改不覆盖总经理当前看到的发布版本。
3. 总经理工作台可进入各部门项目汇总，查看项目名称、负责人、状态、来源部门、更新与发布信息及记录详情。文档生成任务保留独立语义与入口，不与填报记录混成同一类项目。
4. 财务发布后，总经理财务看板显示对应记录及现有口径的指标。售前、工程汇总与财务金额分别展示，避免跨部门重复计数或将预计金额当成合同/应收金额。
5. 其他页面或其他账号发布更新后，已打开的总经理页面通过回到页面、重新聚焦或手动刷新取得最新数据；前台可见时的更新延迟目标不超过 30 秒，使用轮询时必须在失焦/隐藏时暂停，并以实际端到端测试验证。网络故障显示最后更新时间及刷新失败状态，不清空真实旧结果伪装为零。
6. 若员工仅保存草稿，总经理仍显示上次发布版本，并明确数据截止与发布状态；此为既有业务规则，不误报为同步故障。

总经理角色在前端可见与后端 grant/capability 均需验证，不能为了显示数据扩大员工或管理员的业务访问范围。

### 4.1 工程部

1. 进入现有工程成本测算入口，选择“新建测算”，上传 1～2 份 XLSX，填写地区。
2. 页面进入“正在检查清单”。后台只做预检、解析和依据整理，此时不执行成本计算。
3. 显示测算确认单：文件名、文件版本、地区、识别条目、当前引擎实际使用的计价规则，以及阻塞问题和非阻塞提示。
4. 用户处理阻塞问题并核对依据，点击“确认并开始测算”。没有阻塞问题时只需一次确认，不要求逐行批准。
5. 后台自动执行，用户可离开页面；返回同一任务后恢复实际进度和已保存结果。
6. 结果页显示文件成果、现有引擎提供的汇总、来源和待核价事项。未返回的指标显示未知，不由前端编造。
7. 失败时显示失败阶段及操作。重试复用绑定仍有效的结果；修改文件或执行依据产生新版本，旧成果继续保留。

确认单中“地区”等受支持选项必须传入计算。税费、甲乙供、安装范围等只有在现有引擎或输入存在可靠表达且验证可执行时，才能成为可编辑控制项；其余显示为规则说明或待核实项。影响结果且无法表达的歧义作为阻塞项，不能仅添加备注后假装已解决。

结果状态分开显示“程序执行完成”和“仍有待核价事项”；不将内部成本草稿自动变为正式报价。部分成功只能展示已真正保存并校验的文件，不能根据预检结果宣称计算成功。

### 4.2 人事部

1. 用户描述招聘需求，或上传 JD。
2. 页面显示 JD 正文及从该版本得到的必需项、加分项、其他待确认内容。保留未识别原文，不能静默丢弃。
3. 用户可编辑当前草稿；修改结构化条件时必须在正文中有依据。点击“确认岗位标准并用于筛选”，调用现有正式 JD 确认接口。
4. 用户选择该正式 JD，批量上传简历，点击“开始筛选”。已有有效正式 JD 可直接选择，不再重复确认。
5. 后台逐份提取、整理画像、逐项匹配、验证引用并汇总。单份失败不阻止其他简历完成。
6. 结果页提供候选人对比、证据定位、未知项和核实问题；每次最多选择 3 人对比，沿用已有批次访问范围。
7. 重试失败项时只补失败及失效阶段。岗位变化后创建绑定新正式 JD 的新批次，不覆盖历史筛选结果。

核实问题根据岗位条目与已保存证据生成，例如“请核实是否独立承担过项目交付”；必须关联 requirement_id、简历版本及证据位置。UNKNOWN 表示资料不足，不改写为 NOT_MATCH。本期优先使用确定性模板，避免为问题列表再增加模型调用。

### 4.3 共同交互要求

- 普通用户看到业务名称、依据、待办和结果，不展示哈希、租约、缓存键等实现细节。
- 提问集中展示，只要求补充影响执行的关键缺项，不强制多轮聊天。
- 确认按钮有防重复提交；并发版本冲突显示差异并保留未保存输入。
- 使用服务端真实阶段、文件/简历数量展示进度；无法估计时不伪造百分比或剩余时间。
- 刷新、深链接、前进后退、未保存离开和下载保持正常。

## 5. 工程设计

### 5.1 结构

新增工程准备记录及其不可变确认快照；沿用 EngineeringJob 执行原有成本计算。准备记录负责上传预检、依据确认和聚合进度，计算任务只在准备版本确认后创建。

拟新增 `engineering_preparation.py`、`engineering_preparation_api.py`、`engineering_steps.py`；模型和迁移放在工程现有模型体系。路由由 `config/urls.py` 增量注册，不修改产品路由。

准备记录至少保存：owner、version、state、私有文件引用与哈希、地区、预检结果、可执行依据、待核实事项、确认人/时间、确认摘要、幂等键、关联执行任务、创建及更新时间。步骤保存 key、输入绑定摘要、状态、结果摘要、可验证的输出引用、重试次数与错误。

### 5.2 状态与不变量

准备流程：`checking → needs_input / awaiting_confirmation → confirmed → running → completed / partial_failed / failed`。基础设施故障可以进入 `blocked`，恢复后从有效检查点继续。

- 未确认准备版本不能创建新流程的可运行计算任务。
- 确认原子校验 expected_version、basis_hash 和当前授权；并发重复确认只产生同一组任务。
- 修改文件、地区或任何会影响计算的依据必须产生新版本，旧确认不再适用。
- 确认摘要绑定输入、可执行选项、实际使用的规则/价格库版本或内容指纹及实现版本；不能只绑定文件名。
- 执行前再次核对绑定；运行中必须使用固定依据，不能读到中途变化的价格库。无法提供快照时，检测变化后阻塞该步骤，拒绝混合依据的成果。
- 执行参数只由服务端经过校验的字段构造，沿用可信 Python/CLI 路径和输出校验。
- 准备记录状态和计算任务状态分开，保留原 EngineeringJob 枚举及历史任务语义。

### 5.3 API 契约（新增，不替换旧接口）

路径前缀：`/api/engineering/preparations/`。

| 操作 | 请求 | 结果 |
| --- | --- | --- |
| POST 集合 | files、region，Idempotency-Key 请求头 | 201 准备记录；相同键、相同输入返回同一记录，不同输入返回 409 |
| GET 集合/详情 | 原身份与权限 | 本人记录、状态、预检、依据、关联任务和可下载成果 |
| POST `{id}/revisions/` | expected_version、待更新的 files/region | 创建新准备版本，旧确认与成果保留 |
| POST `{id}/confirm/` | expected_version、basis_sha256 | 原子确认精确版本并排队；重复提交不重复计算 |
| POST `{id}/retry/` | expected_version | 仅重试可恢复失败，授权或依据失效时拒绝 |

统一错误：400 非法输入，401 未登录，403 无权限，404 非本人/不存在，409 版本、幂等或依据冲突；基础设施不可用沿用项目现有 503 错误语义。接口拒绝未知写入字段，输出不暴露本机路径。

旧 `/api/engineering/jobs/` 的字段、上传后自动排队、详情和下载保持兼容。新前端只通过 preparations 路径发起新流程；文档明确旧 API 仍按旧行为执行，不宣称全系统所有工程调用都强制经过确认。

### 5.4 执行与恢复

阶段为预检、固定依据、计算、校验、成果保存。成功结果立即持久化，读取时校验绑定及输出完整性。恢复不得仅依据 `completed` 标记跳过文件验证。

文件级恢复需要证明与原 CLI 的多文件行为等价：先以 1 份、2 份合成清单验证拆分不会改变计算或汇总语义，才允许按文件创建执行单元；若存在文件间依赖，则保持关联文件整体执行，明确报告该恢复粒度，不能擅自拆分。

网络/暂时性故障按既有上限有限重试；输入错误、缺失事实和依据冲突不自动循环。租约失效的旧 Worker 不能覆盖新执行结果。成功文件原有下载仍可使用，只有校验通过且确实保存的成果可以出现在结果列表。

## 6. 人事设计

### 6.1 岗位标准

复用 RecruitmentRequest、JDVersion 和现有 confirm 接口，不新建第二套岗位审批。移除上传页面的自动确认调用，在确认之前允许预览、修改并保留草稿。

现有 `hard/bonus` 分类、`MATCH/PARTIAL/UNKNOWN/NOT_MATCH` 判断和辅助分计算保持不变；可协商要求先通过现有正文与备注表达，不顺带引入新评分类别。未确认或过期 JD 不可创建新的筛选任务。

### 6.2 阶段保存与复用

增加独立的人事阶段结果记录，建议文件 `hr_resume_steps.py`，不直接调用产品专用 run_step。

| 阶段 | 输入绑定 | 可复用条件 |
| --- | --- | --- |
| 提取 | 用户与当前授权边界、文件哈希、提取器/OCR版本及相关模型配置 | 同一用户、来源仍有效、文件和实现一致 |
| 画像 | 提取结果摘要、画像字段/提示规则、模型及配置版本 | 上述条件与结果完整性均有效 |
| 匹配 | 简历解析摘要、精确 JD 及条件摘要、匹配规则和模型配置 | 仅同一有效岗位依据复用 |

- 提取/画像成功后立即保存；匹配失败不丢弃已完成解析。
- 跨岗位复用仅允许同一用户、当前仍可访问且 active 的来源；不跨用户共享。
- 缓存不承担授权。每次读取、模型调用前和写入前重新核对权限、归档状态及有效版本。
- 缓存绑定排除无关 JD 字段，以支持换岗位复用解析；匹配绑定必须包含正式 JD 与完整条件。
- 来源归档、删除、撤权后不可继续复用；清理不得删除仍被其他有效本人记录引用的结果。保留引用与授权校验测试。
- 新增模型配置或提取器版本变更导致相关缓存失效，不依赖可变模型显示名称判断。
- 成功阶段带校验摘要；内容损坏、缺少必要证据或来源无效时视为未命中。
- 同一简历并发命中/计算采用唯一约束及租约；不长时间持有数据库锁等待模型。

### 6.3 结果与兼容

现有上传、run、retry、summary、detail、CSV 与下载接口路径保留；允许增加向后兼容的 stage_progress、reused_stages、verification_questions 等字段。

重新筛选使用新正式 JD 创建新批次，再上传同一简历触发解析复用。沿用当前上传去重和文件上限，不要求本期增加服务器端跨批次复制简历接口。

候选人对比只使用当前批次已有、已授权的结果；问题列表从存储的匹配矩阵生成，与详情、导出中展示的版本一致。原评分不因展示方式改变；不自动生成录用或淘汰结论。

## 7. 同步策略、修改边界与迁移

### 7.1 同步策略决策

当前决定：优先保留“各部门台账及不可变发布版本”作为权威数据源，用总经理查询与页面汇总读取这些数据。这个场景主要是同一系统的数据读取，暂不引入消息队列、双向复制、独立同步服务或统一项目主库。

依据：已有售前发布可见性测试通过，工程/财务已有项目读取接口；当前更需要验证前端是否消费正确接口、权限是否匹配、读取是否停留在旧版本，而不是先替换已经存在的数据生命周期。

实施者自行进行下列决策，不把技术选型再次交给用户：

- 接口正确但页面漏接、筛选不一致或刷新过期：修复页面接线、参数、缓存失效与版本展示。
- 保存/发布与查询数据源不一致：在现有台账模块内统一权威读取及事务边界，补充失败与并发回归。
- 重复查询逻辑造成三部门行为漂移：提取必要的部门查询/展示适配，保留既有接口兼容。
- 只有能够复现既有结构无法满足本期验收，才执行相关模块的局部重构；在执行报告中对比修改前后失败场景、影响范围、兼容性与回退路径。

不得把三部门同名项目自动视为同一个项目。总经理聚合至少以部门和来源记录标识区分；保留现有部门内部历史分组行为，新增汇总不能扩大为跨部门同名合并。

## 10. 风险与回退
