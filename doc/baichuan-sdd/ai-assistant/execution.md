## 1. 启动和恢复

每次开始或上下文丢失后：

1. 阅读根目录 `AGENTS.md`、本包 README、`progress.md`、`checkpoint.json`；定位 `tasks.md` 中当前任务及依赖。
2. 读取实际 `git status`、HEAD、相关差异和证据。保护用户已有未提交文件；不为恢复进度重置工作区或强制切换版本。
3. 阅读当前任务关联的需求和验收，确认代码、运行环境与已记录信息一致。历史远程部署回执不等于当前本地运行事实。
4. 用实际证据核实上次完成的最近工作单元，再从检查点的下一动作继续；不要重跑所有历史研究、重导全库或重建已存在资料。
5. 在开始时更新当前任务为 IN_PROGRESS，记录时间和本轮范围。若用户只要求方案/评审，保持实施未启动；后续明确要求开始实施后在其范围内自主推进。

如果检查点与代码不一致，先记录差异并修正状态，不能为了凑进度把未验证工作当完成。文档设计变动先更新规格和受影响验收再改实现；技术细节在授权范围内自行决策并记录。

## 2. 工作单元与持续执行

一个工作单元应能独立检查和恢复，例如：一个匹配规则、一组权限接口、一个可恢复任务阶段或一批企业资料研究。避免到任务结束才一次性记账。

- 根据依赖选择任务，完成实现和必要检查后再推进；遇到缺口继续做不依赖该缺口的工作，不因普通困难暂停整个任务。
- 既定范围内无需逐条请求批准。确实缺少访问能力、影响业务含义的无法消除歧义、付费/破坏性操作或超出授权的外部发布，先完成可独立完成的工作，再说明具体依赖；不能假定等待时间等于用户批准。
- 复杂问题允许自主研究 GitHub 公开实现与官方资料。按 decisions.md 留下最小必要的来源/版本/许可证/验证记录，不无限选型。
- 在持续交互的工作期间，约每 60 秒以内提供简明进展，说明已确认事实、尚未解决点和接下来验证什么，不反复播报相同状态。
- 不因“长任务”自行创建定时自动化、跨聊天发消息或启动其他代理；这些行为遵守用户实际授权和工具规则。

## 3. 检查点更新

完成每个可验证单元、每批研究写入、切换阶段、遇阻、准备中断和交付前，都更新进度与检查点。特别长的操作使用工具已有的任务/会话 ID；不依赖一个不留状态的长脚本完成全部企业。

`progress.md` 记录：

- 本轮任务 ID、状态、时间与环境类型。
- 实际改动文件/数据范围，规格或决策变化。
- 执行过的检查、结果、证据路径及未覆盖项。
- 用户文件保护情况、未解决依赖和下一条具体动作。

`checkpoint.json` 至少保持：范围版本、实施授权状态、当前/下一任务、工作区基线、最后完成单元、检查记录、依赖、证据引用与恢复步骤。更新时保持合法 JSON，并让其与 tasks.md 一致；不把密钥、数据库密码、完整联系人或原始招标文本写入。

### 运行时检查点（存入已确认部署的受控数据库/存储）

全库研究保存清单 ID、固定总数、批次、每家公司/字段/来源的状态、修订号、失败原因和重试时间。任务保存租约/fence、预算、已完成阶段及结果引用；每个事实修订与工作项状态保持事务一致或使用可恢复提交协议，不能出现“标完成但事实未落库”。

运行时批量敏感数据不进入开发文档或 Git。脱敏开发记录引用运行任务 ID、数据数量与报告哈希即可。外部受控位置在 AI-T01 确认，不能预设临时剪贴板和本机 output 目录永久可用。

AI-D19后独立辅助研究以所属本地私有固定manifest、逐企业来源/缺口和coverage收据恢复；公开资料维护批次必须绑定实际读到的原文hash、ID/名称/版本并先在线备份。企业事实及批次完成标记同事务提交，文件检查点迟于事务时重放读取完成标记。正常查询/上传/追问/重试不触发研究；辅助收据不能擅自重置原后台失败队列。覆盖报告分别计发现尝试、可读正文、实际补空、完整研究及发证机构核实。

## 4. 验证和状态

先运行当前改动需要的检查；通过后只有新改动、失败或未解决风险才扩大/重复检查，避免反复跑无关全套。

- 需求行为由服务层/前端/集成测试及必要真实浏览器操作验证；纯文档校验使用路径、编号、映射和状态一致性检查即可。
- 匹配必须覆盖未知、冲突、主体、等级方向和相关日期；任务必须覆盖崩溃恢复及过期执行者；资料维护必须覆盖人工并发修改。
- 未执行记 NOT_RUN；失败记 FAIL；缺来源/能力如实记录，不能写 PASS。仅凭代码已写、模型说完成或旧证据不能完成任务。
- 一个任务 DONE 前检查：交付物存在、关联条件实际满足、证据可定位、状态同步且下一步清楚。任务中仍有重要未验收子项则保持 IN_PROGRESS 或 BLOCKED。
- 全库研究中的某企业“已研究但仍有缺口”可以完成该次研究工作项，但报告仍保留未核实字段；不得把字段状态同步改为 verified。

## 5. 卡点、失败与范围变化

记录具体错误、重现条件和已尝试方法；按预算有限重试。外部不可访问可以换合法来源，不绕过访问限制，也不反复查询同一个确定失败地址。

如果需用户信息，用一个清楚问题指出真正缺失的信息，并继续独立工作。用户已给的授权和偏好持续有效，不为同一步骤重复确认。用户新约束优先，必要时更新决策、规格、任务和验收映射；不能默默扩大为采购、自动联系企业或重建全库。

不能完成整体目标时保存可恢复产物与真实状态，说明哪个任务卡在哪项依赖；不要把停止本轮写成“全部完成”。
